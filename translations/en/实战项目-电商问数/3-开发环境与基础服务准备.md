## 2. Creating the Backend Project and Using uv

### 2.1 Why This Project Uses uv

Official website: https://docs.astral.sh/uv/

First, understand it in one sentence: `uv` is a modern tool for managing Python projects, virtual environments, and dependencies.

This chapter first needs to establish an understanding: this project aims to adopt an approach that is closer to **real enterprise development engineering practices**, rather than just making the code "runnable."

In the Python ecosystem, the more familiar traditional approaches usually fall into two categories:

- Use `venv + pip` in combination, where `venv` is responsible for creating virtual environments and `pip` is responsible for installing dependencies.
- Use `conda` directly, which manages both the environment and dependencies in a unified way.

In this project, however, `uv` was chosen. Compared with traditional approaches, it is more like an **all-in-one solution**: actions such as creating a project, creating a virtual environment, installing dependencies, removing dependencies, and synchronizing the environment are unified into the same set of commands.

Its main advantages are:

- **Faster**: `uv` is written in `Rust`, and environment creation and dependency installation are usually faster than with traditional approaches.
- **More convenient for engineering**: Project initialization, dependency management, and virtual environment management are unified into one set of commands.
- **Better suited for team collaboration**: Dependencies are written into `pyproject.toml` and lock files, making it easy for others to quickly synchronize the environment after pulling the project.

One-sentence summary: **In "Shopkeeper Data Q&A," `uv` is responsible for managing both the virtual environment and project dependencies, and is the foundational tool for the backend development environment.**

> **Supplementary understanding: the relationship between `uv` and `venv`**
>
> You may ask: since we are using `uv`, why do we still see `.venv` in the project directory?
> The reason is not complicated: at the virtual environment level, `uv` still fundamentally works around Python's `venv` mechanism.
> In other words:
>
> - `venv` is responsible for the "virtual environment" itself
> - `uv` is responsible for integrating processes such as "creating the environment, initializing the project, installing dependencies, and locking versions"
>   Therefore, it is normal for `.venv` to appear in the project directory, and it does not mean that `uv` is not being used.

### 2.2 Installing uv

Before using `uv`, you need to install it into the system environment first.

The most direct method is to use `pip`:

```bash
pip install uv
```

If the download speed is slow, you can also use a domestic mirror:

```bash
pip install -i https://pypi.tuna.tsinghua.edu.cn/simple uv
```

If you are using macOS, run:

```bash
brew install uv
```

**Note:**

- This step does not require activating an existing virtual environment first.
- What is installed here is the system-level `uv` tool.
- Later, when creating a specific project, `uv` will generate an independent `.venv` for that project.

After installation, you can check it first:

```bash
uv --version
```

If it outputs the version number normally, it means `uv` is ready to use.

```bash
didilili@DidililiMacBook-Pro shopkeeper-agent % uv --version
uv 0.11.6 (65950801c 2026-04-09 aarch64-apple-darwin)
```

Seeing the version number is enough; it does not need to match the example here exactly.

### 2.4 Common uv Commands

In this project, the most commonly used `uv` commands actually fall into three categories:

- Add a dependency: `uv add`
- Remove a dependency: `uv remove`
- Synchronize dependencies: `uv sync`

**Adding dependencies**

If you want to add a new dependency to the current project, you can use:

```bash
uv add 包名
# 例如
uv add fastapi
```

After execution, the dependency will be written into `pyproject.toml`.

**Removing dependencies**

If you want to remove a dependency, you can use:

```bash
uv remove 包名
# 例如
uv remove fastapi
```

**Synchronizing dependencies**

`uv sync` is a very important command in this project. Its role can be simply understood as:

> Based on the project's current `pyproject.toml` and `uv.lock`, synchronize your local environment to the correct state.

For example, when you receive project code from someone else, the most common practice is not to install dependencies one by one yourself, but to directly run:

```bash
uv sync
```

This will read the dependencies already declared in the project and automatically bring the environment up to date.

## 3. Create the basic services required by the backend

In addition to the frontend and backend code environments, this project also depends on several basic services. Let's first build an overall understanding here; the next chapter will continue with the specific configuration of these basic services.

### 3.1 Overview of basic services

This project mainly uses the following services:

| Service                       | Main purpose                                                                                                                                                                                             |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `MySQL`                    | Used to store metadata information for the data warehouse, including table information, field information, and metric information; it also serves as a business data warehouse to simulate a real warehouse scenario                                                                                       |
| `Qdrant`                   | Serves as the vector database to store vector representations of field and metric information; when a user asks a question, the system retrieves the most relevant metadata through semantic similarity, providing highly relevant context for generating SQL                                                        |
| `Elasticsearch`            | Builds an inverted index for the actual values of each dimension field; when a user's question contains natural language descriptions such as "North China region" or "digital product category", full-text search can match the actual field values in the database, providing a basis for `WHERE` conditions or `GROUP BY` grouping when generating SQL |
| `Kibana`                   | Elasticsearch's visual management and debugging interface, used for index management, query debugging, and retrieval effectiveness verification, making it convenient to observe and optimize retrieval behavior during development                                                                                 |
| `Text Embedding Inference` | Used to deploy the Embedding model inference service, converting metadata text and user questions into vector representations, providing the vector data source for `Qdrant` and serving as the foundation for semantic retrieval capability                                                                            |

From the perspective of overall division of labor, they are essentially a set of basic services that cooperate with each other: `MySQL` is responsible for storing structured data, `Qdrant` is responsible for semantic similarity retrieval, `Elasticsearch` is responsible for full-text matching, `Kibana` is responsible for debugging and validating retrieval effectiveness, and the Embedding service is responsible for converting text into vectors.

> The backend code is responsible for "organizing workflows," while these basic services are responsible for "providing data, retrieval, and vectorization capabilities."

### 3.5 How to start the services

Now that Docker has been installed and configured, and started successfully, next we configure the basic services required by this project. In the root directory of the `shopkeeper-agent` repository, there is a `docker` directory containing the following files:

- `docker-compose.yaml`
- `mysql` initialization script
- `elasticsearch` custom image build file

#### 3.5.1 Prepare the Embedding model before starting

There is a preliminary step that is easy to miss: the Embedding model needs to be downloaded separately.

The project loads `BAAI/bge-large-zh-v1.5` through `Text Embeddings Inference`. This model file is relatively large and has not been directly committed to the Git repository. In other words, the repository has the `docker/embedding/` directory convention, but before starting the basic services for the first time, you need to place the model file in it.

The local directory required by the project is:

```text
shopkeeper-agent/docker/embedding/bge-large-zh-v1.5
```

In the root directory of the `shopkeeper-agent` project, you can use the following command to download:

```bash
uv run hf download BAAI/bge-large-zh-v1.5 --local-dir docker/embedding/bge-large-zh-v1.5
```

If you download the model manually, you should also place the extracted model files in the same directory. The directory should at least contain files similar to the following:

```text
config.json
tokenizer.json
tokenizer_config.json
pytorch_model.bin
vocab.txt
```

Later, the Embedding service in `docker-compose.yaml` will read the model files here through directory mounting:

```yaml
volumes:
  - ./embedding/bge-large-zh-v1.5:/models/bge-large-zh-v1.5
```

If this directory does not exist, or it does not contain complete model files, the Embedding container, even if started, will not be able to provide vectorization services properly. Subsequent construction of the metadata knowledge base, field vector index, and metric vector index will all depend on it, so it needs to be prepared before the first `docker compose up -d`.

#### 3.5.2 Start the basic services

You can follow these steps:

1. Enter the directory where `docker-compose.yaml` is located
2. Execute `docker compose up -d` to start the entire set of services

The first startup may take a long time because images need to be downloaded; subsequent startups will be much faster.

## 4. Analysis of the docker-compose.yaml file

### 4.1 Basic understanding

Project file path: `shopkeeper-agent/docker/docker-compose.yaml`

```yaml
services:
  mysql:
    image: mysql:8.0
    container_name: mysql
    restart: unless-stopped
    environment:
      MYSQL_ROOT_PASSWORD: dili123
      MYSQL_USER: didilili
      MYSQL_PASSWORD: dili123
    ports:
      - "3306:3306"
    volumes:
      - mysql_data:/var/lib/mysql
      - ./mysql:/docker-entrypoint-initdb.d
    command: --character-set-server=utf8mb4
      --collation-server=utf8mb4_general_ci

  elasticsearch:
    build: ./elasticsearch
    container_name: elasticsearch
    restart: unless-stopped
    environment:
      discovery.type: single-node
      xpack.security.enabled: "false"
    ports:
      - "9200:9200"
    volumes:
      - es_data:/usr/share/elasticsearch/data
  kibana:
    image: kibana:8.19.10
    container_name: kibana
    restart: unless-stopped
    environment:
      ELASTICSEARCH_HOSTS: http://elasticsearch:9200
    ports:
      - "5601:5601"
    depends_on:
      - elasticsearch

  qdrant:
    image: qdrant/qdrant:v1.16
    container_name: qdrant
    restart: unless-stopped
    ports:
      - "6333:6333" # HTTP
      - "6334:6334" # gRPC
    volumes:
      - qdrant_data:/qdrant/storage

  embedding:
    image: ghcr.io/huggingface/text-embeddings-inference:cpu-1.8
    platform: linux/amd64
    container_name: embedding
    restart: unless-stopped
    ports:
      - "8081:80"
    environment:
      MODEL_ID: /models/bge-large-zh-v1.5
      MAX_CONCURRENT_REQUESTS: "16"
      MAX_BATCH_TOKENS: "16384"
    volumes:
      - ./embedding/bge-large-zh-v1.5:/models/bge-large-zh-v1.5

volumes:
  mysql_data:
  es_data:
  qdrant_data:
```

If you only understand `docker compose up -d` as "a startup command," you will miss an important layer of engineering understanding. The `Compose` file is not just about typing fewer commands, but about using a single configuration file to clearly describe "which services this project depends on, how these services start, how ports are mapped, how data is persisted, and how directories are mounted."

In "Shopkeeper Data Q&A," this `Compose` file can be understood as: a basic service manifest. That is to say, it does not describe a single container, but rather "what types of containers need to work together to get this project running."

### 4.2 Basic service descriptions

- MySQL container: responsible for the metadata database and simulated data warehouse
- Elasticsearch container: responsible for full-text retrieval
- Kibana container: responsible for visual operations on Elasticsearch
- Qdrant container: responsible for vector retrieval
- Embedding service container: responsible for converting text into vectors

Looking at these services together, you will find that this file actually prepares not five scattered containers, but three types of basic capabilities:

- **Structured data capability**: MySQL
- **Full-text retrieval capability**: Elasticsearch + Kibana
- **Vectorization and vector retrieval capability**: Embedding service + Qdrant

This is also why it is so important. The subsequent data Q&A flow, metric matching, and retrieval recall are not accomplished by business code alone, but are built on the premise that these types of foundational capabilities are already prepared.

### 4.3 Detailed Explanation of Configuration Items

If you continue reading through this `Compose` file, the following types of configuration are the most important to understand first:

- `image`
  Indicates directly using a ready-made image, for example, `mysql:8.0`, `kibana:8.19.10`, `qdrant/qdrant:v1.16`.

- `build`
  Indicates not directly using a ready-made image, but first building the image based on the `Dockerfile` in the current directory. Here, `elasticsearch` uses `build: ./elasticsearch` because it is usually necessary to install an additional Chinese word segmentation plugin.

- `container_name`
  Used to give the container a more intuitive name, which makes it more convenient to view later in `Docker Desktop` or on the command line.

- `restart: unless-stopped`
  Indicates that if the container stops due to an abnormal reason, it will restart automatically; only when you manually stop it will it no longer be automatically brought back up.

- `environment`
  Used to inject the environment variables required at startup into the container. For example:
  - MySQL is configured here with `MYSQL_ROOT_PASSWORD`, `MYSQL_USER`, `MYSQL_PASSWORD`, used to initialize the database password and regular user.
  - Kibana connects to Elasticsearch here through `ELASTICSEARCH_HOSTS`.
  - The Embedding service specifies the model directory to load here through `MODEL_ID`.

- `ports`
  Used for port mapping between the host machine and the container. For example:
  - `3306:3306` means the local machine accesses MySQL through `3306`.
  - `9200:9200` means the local machine accesses Elasticsearch through `9200`.
  - `5601:5601` means the local machine opens Kibana through `5601`.
  - `6333:6333` and `6334:6334` correspond to Qdrant's HTTP and gRPC ports respectively.
  - `8081:80` means the local machine accesses the Embedding service through `8081`.

- `volumes`
  Used for data persistence or directory mounting. This item is very important, because if it is not mounted, after the container is deleted, the data or files inside will usually be lost as well.

  First, let's distinguish the two most common ways of writing this:
  - **Named volume**
    In the form `mysql_data:/var/lib/mysql`. The `mysql_data` on the left is not a folder in the current directory, but a persistent storage area managed by Docker; the `/var/lib/mysql` on the right is the directory inside the container.

  - **Bind mount**
    In the form `./mysql:/docker-entrypoint-initdb.d`. The `./mysql` on the left is a real folder in your current project directory; the `/docker-entrypoint-initdb.d` on the right is the directory inside the container.

  The core difference between these two ways of writing can be remembered in one sentence:
  - **Named volumes** are more suitable for storing "data generated after the container runs."
  - **Bind mounts** are more suitable for giving "existing files on the host machine" to the container for use.

  You can also add a most direct rule of thumb for judgment:
  - If the left side is `./xxx`, `../xxx`, `/绝对路径/xxx`, it is usually a **bind mount**.
  - If the left side is just a name like `mysql_data`, `es_data`, `qdrant_data`, it is usually a **named volume**.

  There is also a very critical but also most easily confused point here:
  - **Deleting the container** does not mean deleting the named volume.
  - **Deleting the container** usually does not mean deleting the mount directory on the host machine either.

  In other words, as long as what you delete is the container itself, and you did not also delete the corresponding volume or the host machine directory, then the data is usually still there. What really tends to cause data loss is often not the step of "deleting the container," but deleting the volume together with it, or manually deleting the mount directory on the host machine.

  Combined with this current `docker-compose.yaml`, it can be understood item by item like this:
  - `mysql_data:/var/lib/mysql`
    This is the persistence of MySQL's data directory. MySQL's actual data files will be written to `/var/lib/mysql` inside the container, and `mysql_data` is responsible for preserving this data long-term. This way, even if the MySQL container is deleted, as long as this volume is not deleted together with it, the database data is usually still there.

  - `./mysql:/docker-entrypoint-initdb.d`
    This mounts the initialization SQL scripts from the project into the MySQL container. When the official MySQL image starts for the first time, it automatically executes scripts in the `/docker-entrypoint-initdb.d` directory, so the purpose here is not to "save data," but to "give the database creation, table creation, and data initialization scripts to the container for execution."

  - `es_data:/usr/share/elasticsearch/data`
    This is the data persistence directory for Elasticsearch. If it is not mounted, index data will follow the container's lifecycle; once the container is deleted, the full-text search data is also easily lost.

  - `qdrant_data:/qdrant/storage`
    This is the vector data persistence directory for Qdrant. Its idea is the same as MySQL and Elasticsearch: to keep the data required for retrieval in Docker's persistent storage, rather than only inside the container.

  - `./embedding/bge-large-zh-v1.5:/models/bge-large-zh-v1.5`
    This mounts the local Embedding model directory from the host machine into the container. What is mounted here is not database data, but the model files themselves. After the container starts, it will read the model weights from `/models/bge-large-zh-v1.5`.

  In addition, the section at the bottom:

  ```yaml
  volumes:
    mysql_data:
    es_data:
    qdrant_data:
  ```

  Indicates that this Compose file additionally declares 3 **named volumes**. Its meaning is: the services above are using these volumes, and here they are defined uniformly.

  If `volumes` is compressed again into one sentence that is easiest to remember, it can be understood like this:
  - The left side determines "where the data or files come from."
  - The right side determines "where the container goes to read or write."

- `depends_on`
  Used to express dependency relationships between services. For example, if `kibana` depends on `elasticsearch`, it does not mean "wait until all of Elasticsearch's business states are completely normal before starting," but rather "start the dependent service first, and then start the current service."

You can read a `Compose` file in this order:

1. Look at which services are defined in `services`.
2. Look at whether each service is `image` or `build`.
3. Look at `ports`, and confirm through which ports the local machine accesses them.
4. Look at `volumes`, and confirm which data will be written to the host machine.
5. Look at `environment`, and confirm what configuration this service depends on when starting.
6. Look at `depends_on`, and confirm the dependency relationships between services.

### 4.4 Specific Analysis of Engineering Approach

Looking again at each service itself, this `Compose` file also reflects several important engineering approaches:

- **MySQL is not just starting a database container.**
  It also mounts the initialization script directory through `./mysql:/docker-entrypoint-initdb.d`. This way, when the container starts for the first time, it automatically executes the SQL files in it, initializing the `meta` database, the `dw` database, related table structures, and mock data all at once.

- **MySQL's data directory is persisted separately.**
  The purpose of `mysql_data:/var/lib/mysql` is to mount the directory where MySQL actually stores data. This way, even if the container is deleted, the data will not be lost due to the container's disappearance.

- **Elasticsearch uses `build` instead of `image`.**
  This is because the full-text search in the project is a Chinese-language scenario, which usually requires installing the additional `IK` tokenizer, so it cannot simply be done with a native image.

- **Kibana is essentially a debugging interface for Elasticsearch.**
  It is not a necessary core storage service, but it is very useful during the development stage, because you can directly observe indexes, execute queries, and verify retrieval results through the Web page.

- **Qdrant exposes two types of ports at the same time.**
  One is the more commonly used HTTP port, and the other is the gRPC port. In a teaching project, it is usually enough to prioritize HTTP, but exposing both ports makes subsequent expansion more convenient.

- **The Embedding service is deployed separately as an independent container.**
  This means that the task of "converting text to vectors" is not coupled within the business code, but is provided as an interface through a separate inference service, so that the backend code only needs to call the service.

  It can also be additionally understood here that Embedding is not limited to being deployed only in this "independent service" way. It can also be directly coupled within the business code, that is, the backend program loads the model itself and completes the text-to-vector process itself. It is just that this current tutorial chooses the solution of "deploying it separately as an inference service" in order to make the engineering structure clearer and the service responsibilities more independent.

  What runs in this container is also not the kind of "conversational large language model" we usually understand, but an Embedding model specifically responsible for converting text into vectors. Its responsibility is not to generate answers, but to encode texts such as field descriptions, metric descriptions, and user questions into vectors for subsequent vector retrieval.

- **The Embedding service mounts a local model directory.**
  The purpose of `./embedding/bge-large-zh-v1.5:/models/bge-large-zh-v1.5` is to map the local model weights into the container, and then tell the service where to load the model from through `MODEL_ID`.

- **The teaching environment uses the CPU version of the Embedding service.**
  This is mainly to lower the barrier to local deployment. In a real production environment, if higher performance is sought, the GPU version is usually used instead.

If this entire section is compressed into one sentence that is easier to remember, it can be understood like this:

> **The value of this `Compose` file is not just starting containers, but preparing the entire set of foundational capabilities of "database, retrieval, and vectorization" all at once.**
